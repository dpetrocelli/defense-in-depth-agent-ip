\section{Experimental Methodology}
\label{sec:methodology}

\subsection{Evaluation Dimensions and Metrics}

Security effectiveness is measured on two complementary levels. Controlled penetration testing verifies each mechanism against a fixed set of test cases with a pass/fail criterion. Live evaluation submits attack and legitimate queries to a deployed agent and measures the \emph{block rate}, the share of attack queries that do not obtain a substantive answer, and the \emph{false-positive rate} (FPR), the share of legitimate queries that are blocked. The new experiments add the \emph{attack success rate} (ASR), the share of attack queries whose final response leaks protected content, so that blocking and leakage are measured separately. Performance overhead is measured as the latency added by each layer at the 50th, 95th, and 99th percentiles (P50, P95, P99) and as the throughput under concurrent load. Deployability is assessed through the monthly infrastructure cost of the defense layers on three providers.

\subsection{Penetration Test Suite}

The controlled suite comprises 63 test cases in 12 categories aligned with the OWASP LLM Top~10~\cite{owasp2025} and the NIST taxonomy of adversarial machine learning~\cite{nist2025aml}. Every test specifies the attack vector, the targeted security goal, the defense layer expected to intercept it, the payload, and the pass/fail criterion. The categories cover representative attack patterns from established taxonomies rather than an exhaustive adversarial exploration.

\subsection{Attack Corpus and Legitimate Queries}
\label{sec:corpus}

The live evaluations use a corpus of 42 attack queries organized in eight categories of increasing sophistication: naive extraction (8), instruction override (5), jailbreak and persona change (7), encoded payloads (4), typoglycemia (4), social engineering (5), indirect injection through fake system markers (4), and multi-turn escalation (5). The corpus is complemented by 23 legitimate queries in three length groups (10 short, 10 medium, and 3 long), which are used to measure false positives. In the live evaluation of Section~\ref{sec:live}, an attack query counts as blocked when the request is rejected, when the response is empty, or when the response consists of a refusal; a legitimate query counts as a false positive under the same criterion. The multi-model evaluation and the ablation study refine this criterion with the per-request outcome classification of Section~\ref{sec:multimodel-protocol}.

\subsection{Deployment Environments}

Two environments are used. The cloud environment is the two-account AWS deployment of Section~\ref{sec:implementation}, with Amazon Nova Lite as the underlying model; it supports the live evaluation, the performance measurements, and the cost analysis. The local environment is the multi-account Docker Compose stack of Section~\ref{sec:local-env}, which runs the same agent and gatekeeper code against open-weight models served by Ollama; it supports the multi-model evaluation and the ablation study. In both environments the experiments use the test prompts of the corpus rather than a production prompt.

\subsection{Multi-Model Evaluation Protocol}
\label{sec:multimodel-protocol}

The multi-model evaluation answers RQ1 by holding every element of the pipeline fixed and varying only the underlying LLM, so that differences in outcome can be attributed to the model. Table~\ref{tab:model-roster} lists the nine models, which span six families and both deployment modes of the architecture: Amazon Nova Lite is invoked through the managed inference service of the cloud environment and serves as the reference model of the live evaluation, while the eight open-weight models are served by Ollama in the local environment. All models run the same agent and gatekeeper code.

The following factors are fixed across models. The base system prompt is the medium-length prompt of the corpus (about 600 characters), whose closing sentence is a minimal confidentiality instruction that forms part of the base prompt in every configuration. The prompt is hardened with the production defensive suffix and the canary tokens of Section~\ref{sec:hardening}, and the agent exposes its four demonstration tools. Decoding is deterministic where the runtime allows it (temperature 0, nucleus sampling disabled), with identical parameters for all models. All four layers are enabled, which corresponds to configuration C4 of Table~\ref{tab:ablation-configs}. Every query is submitted in a fresh conversation, with the exception of the multi-turn escalation category, whose five queries form one session and are submitted in their listed order. Each model is evaluated in three independent runs; results are reported as mean and standard deviation. Requests that end in a transport error or a timeout are counted as errors, reported separately, and excluded from the denominators.

The outcome of every request is classified by the mechanism that determined it: \emph{L2 block} (risk score at or above the threshold), \emph{model refusal} (the model declines before any filtering), \emph{L3 filter} (the response filter replaced the output), \emph{canary} (a canary token appeared in the output), \emph{pass} (a substantive response reached the caller), or \emph{error}. Because Layer~2 blocks, canary detections, and model refusals return the same refusal sentence, the label is recorded by the agent as a structured audit field rather than inferred from the response text; the raw model output produced before Layer~3 is recorded as well. Leakage is assessed offline with the same criterion that Layer~3 applies at runtime: a response leaks if it contains a canary token or reproduces any 50-character chunk of the base prompt, ignoring case. The oracle is applied both to the final response, which yields the ASR, and to the raw model output, which yields the \emph{pre-filter leakage} of the model. The block rate is the share of attack queries whose outcome is an L2 block, a model refusal, an L3 filter, or a canary detection; the FPR is the share of legitimate queries with any of these outcomes. Results are reported as overall rates per model (Table~\ref{tab:multimodel-overall}), as block rates per attack category (Table~\ref{tab:multimodel-percategory}), and as the attribution of outcomes to mechanisms (Table~\ref{tab:multimodel-attribution}).

\subsection{Defense-Layer Ablation Protocol}
\label{sec:ablation-protocol}

The ablation study answers RQ2 by measuring how the security outcome changes when individual defenses are removed from the pipeline. The layers are not interchangeable classifiers. Layer~1 governs authentication, request integrity, account binding, and replay protection, and Layer~4 governs monitoring, auditability, and coordinated response; neither acts on the content of a request or a response, so removing them does not change the outcome of the attack corpus. Both are therefore kept active in every configuration and verified separately, with attack cases of their own, in Table~\ref{tab:l1-l4-verification}. The mechanisms that act on the input--output path of a request, and hence on the attack corpus, are the defensive suffix, Layer~2, and Layer~3; the ablation varies these.

\input{tables/tab-ablation-configs}

Table~\ref{tab:ablation-configs} defines the configurations. C0 disables every content defense and measures the floor set by the model itself, since the base prompt retains only its closing confidentiality sentence. C1 adds the defensive suffix alone and isolates the model-side control. C2 and C3 add Layer~2 and Layer~3, respectively, on top of the defensive suffix. C4 is the deployed pipeline and coincides with the condition of the multi-model evaluation. C4$^{\dagger}$ keeps the pipeline of C4 but runs Layer~2 in detect-only mode, in which the risk score is computed and recorded while blocking is disabled; every attack therefore reaches the model and Layer~3, and the verdicts of both layers are observed on the same request. The configurations map directly onto the feature flags of Table~\ref{tab:flags}; the two mechanisms that the reference implementation applies unconditionally, input sanitization and canary detection, follow the Layer~2 and Layer~3 settings, respectively. C0 and C1 expose only the test prompt of the corpus and are executed in the local environment.

All configurations are evaluated for the nine models of Table~\ref{tab:model-roster}, with the fixed factors, repetitions, outcome classification, and metrics of Section~\ref{sec:multimodel-protocol}. The individual contribution of a mechanism is the change in block rate and ASR between configurations that differ only in that mechanism: the defensive suffix from C0 to C1, Layer~2 from C1 to C2 and from C3 to C4, and Layer~3 from C1 to C3 and from C2 to C4. Complementarity is measured on C4$^{\dagger}$: each attack query is labeled with the verdict of Layer~2 (would block or pass) and with its downstream outcome (intercepted by Layer~3 or by a canary, refused by the model, or passed), which yields the contingency table of Table~\ref{tab:complementarity}. Queries that pass Layer~2 and are intercepted by Layer~3 are the direct evidence of complementarity; queries that pass both are evaluated with the leakage oracle to quantify residual exposure. Results are reported per configuration and model in Table~\ref{tab:ablation-results} and per attack category for the cloud reference model in Table~\ref{tab:ablation-percategory}.

Layer~1 is verified with deterministic cases executed against the gatekeeper of the multi-account environment, which runs the production code: a valid signed request must return the prompt with a valid integrity hash, and each violated property must produce the response that follows from the validation order of the gatekeeper without disclosing prompt content. Layer~4 is verified by triggering each event class and checking that the event reaches the central bus and, where an alerting policy applies, that an alert is published on the alert topic, which the environment exposes through a subscribed queue.
